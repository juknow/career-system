커리어 시스템 사용 가이드

이 시스템은 실제 경력 정보와 과거 자기소개서 자료를 활용해, 기업 조사부터 최종 자기소개서 검토까지 이어서 작업하는 데 사용합니다.

처음 한 번: ChatGPT 웹 프로젝트 설정

  1. 일반 ChatGPT 웹을 열고 왼쪽 사이드바에서 새 프로젝트를 선택한 뒤, 예를 들어 Career System이라는 이름으로 만듭니다. Codex를 실행할 필요는 없습니다. ChatGPT 요금제에 따른 사용 한도는 적용됩니다.
  2. 프로젝트의 ··· → 프로젝트 설정(Project settings)으로 이동해 아래 공통 지침을 그대로 복사하여 붙여 넣습니다.

프로젝트 지침에 붙여 넣을 Markdown 원문 — 아래 박스 안의 내용을 제목 기호(#)와 목록 기호까지 전체 복사합니다. Markdown 코드블록을 감싸는 ``` 기호를 추가할 필요는 없습니다.

# 역할
취업 준비를 위한 Career System 프로젝트다. 기업 조사·직무 검토·지원서 전략·자소서 작성·QA에서 프로젝트의 Common Rules와 해당 단계 프롬프트를 적용한다.

# 필수 프로젝트 자료
- Career_System_Common_Rules.md: 상세 작업·검토·승인 규칙의 기준.
- 최신 Career_Master_Profile: 지원자 객관적 경력 사실의 기준.
- Personal_Writing_Knowledge_Base: 과거 자소서의 표현과 인사이트 참고 자료.
필수 파일의 실제 접근 및 최신 버전을 확인하고 접근 불가·불일치 시 사용자에게 최신본을 요청한다. Story Bank는 필요할 때만 참고한다.

# 모든 신규 작업의 사전 승인
요청을 자신이 이해한 목적·범위·실행 계획으로 먼저 설명하고 사용자 확인과 명시적 승인을 받은 후 실행한다. 승인된 하위 단계에는 중복 승인을 요구하지 않는다. 예상 밖의 변경은 별도 승인을 받는다.

# 기업별 실행
프로필 로딩 프롬프트를 반복 실행하지 않는다. 필요 시 지원 가치·중복지원 검토를 거쳐 직무 선정 → 지원서 전체 전략 → 문항별 작성 → 최종 QA를 진행한다. 다른 채팅의 확정 직무·문항별 경험 배정 결과가 현재 채팅에 없으면 필요한 결과만 사용자에게 요청한다.

# 자료 갱신
공통 파일은 프로젝트 소스에 최초 등록하고, 원본이 갱신되면 ChatGPT 프로젝트의 등록 자료도 직접 교체한다. GitHub·Google Drive 간 자동 백업이 ChatGPT 프로젝트 파일을 자동 교체하지는 않는다. 과거 지원서 원문은 필요할 때만 실제 파일을 확인한다.
  1. 프로젝트 소스에 Career_System_Common_Rules.md, 최신 Career_Master_Profile_v1.4.md, Personal_Writing_Knowledge_Base_v0.4.md의 세 파일을 등록합니다. Story Bank는 선택적으로 등록·참조합니다. GitHub 링크만 입력하는 것은 파일 내용을 등록하는 것과 다릅니다.
  2. 프로젝트에 새 기업별 채팅을 만들고 필요하면 선택형 지원 가치 판단부터, 아니면 바로 최종 직무 선정부터 시작합니다. 단계별 프롬프트는 GitHub의 본문 전체를 복사해 사용합니다. 기존 프로필 로딩 파일은 프로젝트 밖 등 공통 파일을 별도로 전달하는 상황에만 선택적으로 활용합니다.
  3. 작업을 시작할 때 최신 프로젝트 자료의 접근·버전을 확인합니다. 파일이 없거나 오래됐다면 소스를 갱신합니다. 새 채팅에서 이전 결정이 보이지 않으면 확정한 결과만 함께 전달합니다.

현재 프롬프트 위치: GitHub의 프롬프트 폴더. GitHub에서 파일을 열고 원문(Raw)을 보거나 본문을 복사하면 됩니다.

ChatGPT 프로젝트 지침은 해당 프로젝트 안의 채팅에 적용됩니다. 프로젝트 파일이나 이전 대화가 어느 채팅에서나 항상 정확히 인용된다고 가정하지 말고, 새 채팅에서 필요한 자료가 확인되지 않으면 다시 제공하세요.

1. 시작 전 준비

먼저 ChatGPT 취업 준비 프로젝트에 아래 세 파일을 필수 등록합니다. Story Bank는 필요할 때 참고하는 선택 자료입니다.

  1. Career System Common Rules — 중요한 판단이나 변경 사항을 최종 반영하기 전에 사용자에게 확인하는 규칙
  2. Career Master Profile — 학력, 프로젝트, 기술, 개인 기여, 확인된 성과와 커리어 선호에 관한 사실
  3. Personal Writing Knowledge Base — 기존 자소서 문항과 재사용 가능한 생각, 관점, 문체를 찾는 자료

과거 자소서 원문은 별도 보관합니다. 프로젝트 소스에 연결된 Google Drive 원본을 실제로 검색하고 열람합니다. 접근에 실패하면 Private GitHub 백업본을 찾고, 두 경로 모두 불가능하면 필요한 원문만 해당 채팅에 첨부합니다. Story Bank는 필요한 사건을 참조하고 사용자 승인에 따라 보강할 수 있습니다.

2. 기업별 실제 사용 순서

공통 실행 방법: 해당 단계의 GitHub 프롬프트 파일을 열고 본문 전체를 복사 → 같은 프로젝트 안의 작업 채팅에 붙여 넣기 → 중괄호 안의 변수에 실제 회사명·공고 URL·질문 등을 입력 → 필요한 첨부를 추가 → 실행합니다. 문항 작성은 해당 기업의 전략 채팅에서 분기하거나 새 채팅으로 시작할 수 있습니다. 새 채팅에서 앞선 결정이 보이지 않으면 확정한 직무와 배정표의 해당 행을 직접 전달합니다.

ChatGPT는 각 신규 작업을 이해한 대로 먼저 설명하고, 사용자의 명시적 승인 후 실행합니다. 이전에 승인된 하위 작업에는 같은 승인을 반복하지 않습니다.

프로필 로딩 단계는 반복하지 않습니다. 처음 등록한 프로젝트 공통 자료를 각 단계에서 직접 참고합니다. 기존 01_Career_Profile_로딩.md는 프로젝트 밖에서 별도 파일을 전달해야 하는 경우에만 선택적으로 사용합니다.

선택 단계. 지원 가치 및 중복지원 확인

실행 파일: 02_지원가치_판단_중복지원_선택.md

지원할지 고민되는 회사이거나 같은 그룹의 여러 공고에 지원하려는 경우에만 실행합니다. 회사명, 현재 채용공고 URL, JD, 이미 지원 중인 공고가 있다면 그 정보도 입력합니다.

확인할 결과: 지원 가능 요건, 회사와 직무의 특성, 지원 준비에 드는 시간, 공식 중복지원 규정, 전형 일정 충돌. 규정이 불명확하면 채용 담당자에게 확인할 사항을 남깁니다.

2단계. 최종 지원 직무 선정

실행 파일: 03_최종_직무_선정.md

회사 공고와 모집 직무를 입력합니다. 선택 단계의 조사 결과가 있으면 함께 전달하고, 없으면 바로 진행합니다.

확인할 결과: 각 직무의 실제 업무, 관련 경험과 부족한 근거, 근무환경, 장기 경력 경로. 비교 결과를 검토한 뒤 지원할 직무를 직접 확정합니다.

3단계. 지원서 전체 전략

실행 파일: 04_지원서_전체_전략.md

확정한 직무와 지원서의 모든 입력 항목·자소서 질문·글자 수를 원문 그대로 입력합니다.

확인할 결과: 프로젝트·활동 입력 방향과 간단한 문항별 경험 배정표. 경험이 적절한지 검토하고 승인합니다. 별도의 Story Map 파일은 만들지 않습니다.

4단계. 자기소개서 문항별 작성

실행 파일: 05_자소서_단일_문항_작성.md

문항마다 새 채팅을 열어 질문 원문, 글자 수, 승인한 경험 배정표의 해당 행을 제공합니다. 프로젝트의 필수 공통 세 파일에 실제 접근할 수 없다면 해당 파일만 요청하고, 이전 채팅의 결정 사항이 보이지 않으면 필요한 확정 결과를 전달합니다.

과거 관련 답변이 Writing Knowledge Base에서 발견됐다면 연결된 Google Drive를 검색해 원문을 직접 열람하고, 실패하면 Private GitHub 백업 또는 해당 채팅 첨부를 이용합니다. 과거의 좋은 관점만 참고하고 이전 회사의 지원동기나 확인되지 않은 사실은 옮기지 않습니다.

확인할 결과: 문항 분석 → 필요한 질문과 작성 방향 확인 → 제출 가능한 초안. 중요한 소재 변경이 제안되면 먼저 결정합니다.

5단계. 지원서 전체 QA

실행 파일: 06_지원서_전체_QA.md

모든 문항의 최종안과 지원서 전체 입력 내용, 확정 직무, 문항별 경험 배정표를 한 채팅에 모읍니다.

확인할 결과: 사실·수치 오류, 경험 중복, JD와의 연결, 과거 회사용 표현, 예상 면접 질문. 수정 제안을 확인한 후 승인한 내용만 실제 지원서에 반영합니다.

3. 새로운 지원서를 다음 지원에 활용하기

지원서 원본(PDF·자기소개서 전체 텍스트)은 공개 GitHub에 올리지 않습니다. 원본은 Google Drive의 Career_Originals/Applications/연도/기업명/에 보관하며, Google Apps Script가 비공개 GitHub의 Career_System/Data/Essay_Archive/연도/기업명/으로 자동 백업합니다. 관련 과거 지원서의 원문이 필요할 때 해당 자료만 ChatGPT 채팅에 첨부합니다. 자동 백업은 본문이나 경력 사실을 자동으로 검증·갱신하지 않습니다.

완성한 지원서의 질문과 답변을 원문 그대로 보관합니다. 필요한 경우 다음 요청문을 별도 채팅에서 사용합니다.

첨부한 지원서의 질문과 답변을 원문 그대로 보관할 수 있도록 정리해 줘. Writing Knowledge Base와 비교해 새롭게 등록할 만한 문항과 인사이트만 먼저 제안하고, 내가 승인한 항목만 파일에 반영해 줘. 새로운 경력 사실이 발견되면 Master Profile 수정안을 별도로 제시해 줘. Experience Story Bank에도 보강이 필요하면 변경할 사건 카드와 출처를 먼저 제시하고 내 승인을 받은 뒤 반영해 줘.

기존 자기소개서 등록이나 경험 갱신을 위해 별도의 전용 프롬프트를 실행할 필요는 없습니다.

3-1. GitHub와 Google Drive 자동 백업 운영

현재 파일별 기준 위치

자료기준 위치자동 반영 위치
공통 규칙·Master·Writing KB·프롬프트·가이드·ReviewPublic career-system의 Career_System/Private career-system-private의 동일 경로
개인 지원서 원본 PDF·MD·TXTGoogle Drive Career_Originals/Applications 아래 연도/기업명Private Career_System/Data/Essay_Archive/ 아래 동일한 연도/기업명
  1. 공통 자료 수정: 사용자 검토·승인 후 Public 저장소의 원본 파일만 수정합니다. 자동화가 Private의 동일 경로로 복제하므로 Private의 공통 파일을 직접 수정하지 않습니다.
  2. 지원서 보관: 최종 원본을 Google Drive의 Applications/연도/기업명/에 저장합니다. 자동화가 Private의 Essay Archive에 사본을 만듭니다. Private에 직접 올린 파일이 Google Drive로 역방향 동기화되는 것은 아닙니다.
  3. 상태 확인: Google Apps Script 프로젝트의 트리거에서 syncDriveToGitHub가 시간 기반 약 5분 간격으로 등록되어 있는지 확인합니다. 실행 화면에서 최신 예약 실행 성공 여부와 오류 메시지를 점검하고, 필요한 경우 Private 저장소에서 실제 파일을 확인합니다. 트리거가 있다고 모든 실행이 성공하는 것은 아닙니다.
  4. 오류 대응: 실패 시 가장 최근의 시간 기반 실행 로그에서 오류 내용을 확인합니다. 인증 오류나 API 호출 한도 초과 등이 발생하면 백업이 지연될 수 있으므로 문제를 해결하기 전 최신 자료가 반영됐다고 가정하지 않습니다. 인증 토큰은 채팅이나 저장소에 공유하지 않습니다.
  5. ChatGPT 자료 갱신: GitHub·Drive의 자동 백업은 ChatGPT 프로젝트의 업로드 파일을 갱신하지 않습니다. Common Rules, Master, Writing KB 등 핵심 파일이 수정됐다면 Public에서 최신본을 받아 ChatGPT 프로젝트 자료를 직접 교체합니다. 사용하는 버전을 확인하고, 필요한 이전 지원서 PDF는 Private 또는 Drive에서 해당 채팅에만 첨부합니다.

중요: 이 동기화는 Public → Private, Drive → Private 단방향입니다. 삭제·경로 변경·접근 권한 문제는 실행 결과를 확인하고 별도로 관리합니다. 문서 내용 수정이나 새로운 경력 사실의 승인은 여전히 사용자에게 있습니다.

3-2. 일반 ChatGPT 웹에서 과거 지원서 원문 찾기

원칙: Writing KB와 Story Bank는 검색을 돕는 색인이고, 실제 문장·수치 비교를 위해서는 원문을 열람해야 합니다. Work 모드로 바꿀 필요는 없습니다.

  1. 프로젝트 소스 연결: 기존 필수 세 MD 파일을 프로젝트에 업로드한 뒤, 같은 비공개 프로젝트의 소스 추가에서 Google Drive Career_Originals/Applications/2026 폴더 링크를 추가합니다. 요구하는 경우 Google Drive 앱 접근 권한을 승인합니다.
  2. 색인 검색: 관련 과거 문항을 Writing KB에서 ID(예: KB26-Q2)로 찾고, Story Bank에서 필요한 사건의 맥락만 보충합니다. Writing KB의 원문 위치 카탈로그에서 회사·연도·파일명을 확인합니다.
  3. 실제 파일 열람: 연결된 Google Drive에서 해당 기업의 Markdown 원문이 있으면 우선 검색해 해당 문항을 읽고, 필요한 경우 PDF를 대조합니다. Google Drive 앱은 프로젝트에서 미리 전체 내용을 동기화하지 않으므로 매 작업에서 실제 접근 가능 여부를 확인해야 합니다.
  4. 대체 경로: Drive에서 원문을 읽지 못한다면 접근 가능한 Private GitHub의 Career_System/Data/Essay_Archive/2026/에서 대응 파일을 열람합니다. PDF가 직접 열리지 않는 등 두 경로 모두 실패하면 해당 원문을 채팅에 첨부합니다.
  5. 대조 후 작성: 실제 열람한 원문 파일과 문항을 밝히고 Master의 객관적 사실, Story Bank의 사건, KB의 재활용 가능한 관점을 대조합니다. 객관적인 경력 정보와 창의적인 서술 후보를 구분해 먼저 사용자에게 검토받습니다.

주의: Google Drive 및 GitHub가 현재 채팅에서 사용할 수 있는 연결 앱인지 확인합니다. 단순히 폴더 링크나 원문 ID가 존재한다는 이유로 파일 내용을 이미 읽었다고 가정하지 않습니다. GitHub 또는 Drive의 변경이 프로젝트에 업로드한 공통 MD 파일을 자동 교체하지도 않습니다.

5. 작업 중 새로운 제안이나 오류가 발견되면

AI는 중요한 변경을 바로 확정하지 않고 먼저 변경 대상과 이유, 선택지를 제시합니다. 사용자는 각 항목을 승인·수정·보류할 수 있습니다. AI는 승인한 범위에서만 진행하고, 파일 변경 내역은 별도의 Review 자료에 정리합니다.

6. 이 가이드를 Notion에 넣는 방법

  1. Notion 웹 또는 데스크톱 앱에서 워크스페이스를 엽니다.
  2. 왼쪽 설정에서 가져오기(Import) → HTML을 선택합니다.
  3. Career_System_사용_가이드_Notion.html 파일을 선택합니다.
  4. 생성된 페이지의 제목과 단계가 잘 들어왔는지 확인하고 원하는 위치로 이동합니다.

Notion에 가져온 뒤에는 위 GitHub 프롬프트 폴더를 북마크하고, 자주 사용하는 단계별 파일 링크를 연결하면 편리합니다. 이 HTML 파일이 GitHub에 올라갔다고 Notion 페이지가 자동으로 업데이트되는 것은 아닙니다.
