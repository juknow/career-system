# 자기소개서 단일 문항 작성

앞선 지원서 전체 전략에서 사용자 승인을 받은 **문항별 경험 배정표**를 입력받아 이번 분기에서는 아래 문항 **하나만** 작성한다. 별도 Story Map 파일을 요구하거나 새로 생성하지 마라.

`Career_System_Common_Rules.md`를 적용한다. 이 독립 채팅에 공통 파일이 없더라도 **새로운 제안 및 필요한 확인을 최종 초안 전에 사용자에게 먼저 제시 → 사용자 결정 → 승인된 범위 작성 → 실제 변경 보고**를 지킨다.

<SELECTED_JOB>
- 회사: {회사명}
- 직무: {직무명}
</SELECTED_JOB>

<ESSAY_QUESTION>
문항: {자기소개서 문항 원문}
글자 수: {제한}
확정 배정표의 핵심 경험: {경험}
보조 경험: {있다면}
관련 과거 자소서 문항 ID(선택): {KB/GS/기타 ID}
</ESSAY_QUESTION>

**참조 자료:** 최신 승인 Career Master Profile(사실 원본), Personal Writing Knowledge Base(과거 질문·인사이트·문체), 필요할 때 해당 원문 Essay Archive. 기존 Story Bank는 동결된 선택 자료로만 사용한다. 동일 경험의 과거 글이 없어도 새 사실을 만들지 않는다.

## 1. 기존 전략 존중
지원서 전체 전략에서 배정한 경험을 우선한다. 다른 문항에 배정된 핵심 경험을 임의로 가져오지 마라. 더 적합한 경험이 있다고 판단하면 **작성 전** 사용자에게 이유·문항 전체에 미칠 영향·대안을 먼저 제시하고 승인을 받아라.

## 2. 실제 사실만 사용
최신 Master에서 확인되는 역할, 직접 행동, 구현·기술 범위, 문제, 의사결정, 성과와 수치만 사실로 사용한다. Writing KB의 인사이트는 과거 해석 후보이지 새로운 결정/감정/대화의 증거가 아니다. 원문에만 있는 행동이 중요하다면 작성 전에 사용자에게 확인하고 승인이 없으면 빼라.

## 3. 평가 의도 분석 후 사전 검토
최종 초안 전에 문항이 요구하는 역량, 반드시 답할 부분, 면접에서 의심할 수 있는 근거 공백, 이번 답변의 핵심 메시지 후보를 간결하게 제시한다. 관련 과거 원문 중 참고할 ID, 재사용할 관점, 재사용하지 않을 업종 포장·미확인 주장도 밝힌다. 필요한 질문과 중요한 개선안을 한 번에 묶어 사용자의 선택을 받는다. **새 제안이 없고 모든 필수 사실이 확인됐다면 기존 승인된 전략 범위에서 초안을 진행할 수 있다.**

## 4. 경험 서술 원칙
프로젝트 소개보다 지원자의 실제 행동과 이유에 집중하라. 필요하면 '상황/문제 → 판단 → 직접 행동 → 선택 근거 → 결과 → 직무 연결' 흐름을 사용하되 모든 문항을 STAR로 강제하지 마라.

## 5. 자소서 문체
JD 복사, 회사 슬로건 반복, 추상적 열정, 공허한 교훈, 기술 나열, 프로젝트 설명 과다, 과도한 미사여구, 기여 과장을 피한다. 구체적 행동과 검증 가능한 결과를 우선하고, Writing KB의 문체를 참고하되 원문을 통째로 복제하지 않는다.

## 6. 회사·직무 연결
경험의 의미가 이번 질문 및 실제 직무와 어떻게 연결되는지 자연스럽게 표현한다. 특히 협업·문제해결처럼 질문이 경험 과정 자체를 상세히 묻는 경우 **마지막 직무 연결 문장을 기계적으로 강제하지 않는다.** 기업 이름을 반복하지 마라.

## 7. 글자 수
기본적으로 제한의 약 90~98%를 목표로 하지만, 내용의 완결성과 요구 분량을 우선한다. 분량을 채우려고 사실을 창작하지 마라. 띄어쓰기 포함/제외 기준이 지정되어 있으면 해당 기준으로 계산하고 실제 계산 불가 시 추정이라고 표시한다.

## 8. 출력 순서
**작성 전 — 사전 검토:**
A. 문항 분석
B. 핵심 메시지 후보 및 활용할 과거 관점
C. 확인이 필요한 사실·전략 변경 제안(있을 경우)
→ 사용자 확인 후 최종 초안 작성.

**승인 범위 내 작성 후:**
D. 제출 가능한 초안
E. 초안의 근거 있는 강점
F. 면접에서 질문받을 수 있는 부분
G. 개선 선택지와 요청할 사용자 확인 사항(있을 경우)

사전 검토에서 필요한 질문이 남아 있으면 그 부분을 창작하지 않고 사용자 답변을 기다려라. 승인되지 않은 사실·핵심 경험 변경은 최종본에 반영하지 마라.
